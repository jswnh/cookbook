# PostgreSQL Data Definition Language (DDL) Syntax

DDL statements define, modify, and drop database schemas and structures. Unlike MySQL, PostgreSQL supports transactional DDL—meaning database schema updates (like table additions or index changes) can be wrapped inside a transaction and rolled back safely if an error occurs.

---

## 1. Schema Management

Schemas are namespaces containing tables, views, indexes, functions, etc.

```sql
-- Create a new schema
CREATE SCHEMA IF NOT EXISTS tenant_a;

-- Set search path to look into specific schemas first
SET search_path TO tenant_a, public;
```

---

## 2. Table Operations

### Identity Columns (SQL Standard)
PostgreSQL 10+ standard replacement for `SERIAL`. 
- **`GENERATED ALWAYS AS IDENTITY`**: Prevents manual values from being inserted (throws error unless `OVERRIDING SYSTEM VALUE` is specified).
- **`GENERATED BY DEFAULT AS IDENTITY`**: Allows manual values, falling back to sequence generation if omitted.

```sql
CREATE TABLE users (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

### Unlogged Tables
Unlogged tables do not write transactions to the Write-Ahead Log (WAL).
- **Benefit**: Extremely fast inserts/updates (often 2-3x write throughput).
- **Risk**: Table data is automatically truncated during database crash recovery. Recommended for temporary caches or session tables.

```sql
CREATE UNLOGGED TABLE session_cache (
    session_key UUID PRIMARY KEY,
    cache_data TEXT,
    expires_at TIMESTAMPTZ
);
```

### Create Table copy syntax
```sql
-- Create table with identical schema (excluding indexes/defaults by default)
CREATE TABLE users_backup (LIKE users);

-- Create table copies, carrying over defaults, constraints, and indexes
CREATE TABLE users_archive (
    LIKE users INCLUDING DEFAULTS INCLUDING CONSTRAINTS INCLUDING INDEXES
);
```

## 3. Constraints

### Basic Constraints
```sql
CREATE TABLE contracts (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    contract_code VARCHAR(20) NOT NULL,
    daily_rate NUMERIC(10,2),
    
    CONSTRAINT uq_contract_code UNIQUE(contract_code),
    CONSTRAINT chk_positive_rate CHECK (daily_rate > 0.00)
);
```

### Exclusion Constraints (Special to PG)
Exclusion constraints use indexes to prevent overlapping ranges or values. Crucial for double-booking prevention.

```sql
-- Requires btree_gist extension for mixing scalar types and ranges
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_bookings (
    room_id INT,
    booking_period TSTZRANGE,
    
    -- Ensure no overlapping booking periods exist for the same room
    CONSTRAINT exclude_overlapping_bookings 
        EXCLUDE USING gist (room_id WITH =, booking_period WITH &&)
);
```
- **`&&`**: Range overlap operator.
- **`=`**: Scalar equality operator.

## 4. Alter Table Operations

PostgreSQL supports highly efficient concurrent alterations.

```sql
-- Add a column with a default value (fast metadata operation in PG 11+)
ALTER TABLE users ADD COLUMN phone_number TEXT DEFAULT NULL;

-- Modify column type (casts existing values using USING)
ALTER TABLE users 
    ALTER COLUMN phone_number TYPE VARCHAR(30) USING phone_number::varchar;

-- Change or drop default value
ALTER TABLE users ALTER COLUMN phone_number SET DEFAULT 'Unspecified';
ALTER TABLE users ALTER COLUMN phone_number DROP DEFAULT;

-- Rename a column
ALTER TABLE users RENAME COLUMN phone_number TO contact_number;

-- Add a constraint
ALTER TABLE users ADD CONSTRAINT chk_username_length CHECK (length(username) >= 3);

-- Drop a constraint
ALTER TABLE users DROP CONSTRAINT chk_username_length;
```

## 5. Declarative Table Partitioning

PostgreSQL supports declarative partitioning based on Ranges, Lists, or Hashes.

```sql
-- 1. Create the partition master table
CREATE TABLE sales (
    id INT GENERATED BY DEFAULT AS IDENTITY,
    amount NUMERIC(10,2) NOT NULL,
    sale_date DATE NOT NULL
) PARTITION BY RANGE (sale_date);

-- 2. Create individual partition tables mapping to the master
CREATE TABLE sales_2024 PARTITION OF sales
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE sales_2025 PARTITION OF sales
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Fallback default partition for anything outside defined bounds
CREATE TABLE sales_default PARTITION OF sales DEFAULT;
```

## 6. Views and Materialized Views

### Views (Virtual Representation)
```sql
CREATE OR REPLACE VIEW active_accounts AS
SELECT id, username, created_at 
FROM users 
WHERE is_active = TRUE;
```

### Materialized Views
Materialized Views physically compute and store the output on disk. Must be manually refreshed to pick up changes in underlying tables. Highly useful for slow analytical aggregates.

```sql
-- 1. Create the materialized view
CREATE MATERIALIZED VIEW monthly_sales_summary AS
SELECT 
    date_trunc('month', sale_date) AS sales_month,
    SUM(amount) AS total_revenue
FROM sales
GROUP BY 1;

-- 2. Create unique index to allow concurrent refresh without locking reads
CREATE UNIQUE INDEX idx_mv_sales_month ON monthly_sales_summary (sales_month);

-- 3. Refresh data in the background (Non-blocking using CONCURRENTLY)
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales_summary;
```
